# Руководство для ИИ-агента

## Цель проекта

Это небольшой Python-сервис интеграции Moyklass с Telegram и MAX. Он принимает вебхуки Moyklass, формирует уведомления о новых платежах и занятиях с задолженностью и пытается доставить их пользователю по номеру телефона через оба мессенджера.

## Карта кода

- `app.py` — FastAPI-приложение, endpoint `/webhook/moyklass`, healthcheck `/health`, asyncio-очереди и фоновые workers, запуск/остановка клиентов и повторные попытки доставки.
- `webhook_handler.py` — маршрутизация событий, запрос данных пользователя/платежа/занятия/группы/курса и подготовка пары `phone` + `text`. Учитывает атрибут пользователя `unsubscribe_automailing`.
- `moyklass_client.py` — синхронный HTTP-клиент Moyklass, получение и кеширование access token.
- `templates.py` — шаблоны сообщений для `payment_new` и `sub_lesson_in_debt`.
- `tg_sender.py` — Telegram-клиент Telethon, поиск пользователя через локальный кеш, диалоги или импорт контакта и отправка сообщения.
- `max_sender.py` — клиент MAX (`maxapi-python`), поиск по телефону, получение чата и отправка; QR-код сохраняется в `max_qr.png`.
- `run_project.py`, `run_project_without_max.py`, `stop_project.py` — Linux-скрипты запуска/остановки через GNU Screen. Первый запускает сервис с MAX, второй — без MAX; скрипты запуска не поддерживают Windows.
- `final_test.py` — интеграционный сценарий, который **создаёт настоящий тестовый платёж** в Moyklass.
- `requirements.txt` — зависимости.

## Основной поток данных

1. `POST /webhook/moyklass` разбирает JSON и помещает `(webhook_id, payload)` в `webhook_queue`, после чего сразу отвечает `{"status":"ok"}`.
2. `webhook_worker` вызывает синхронный `process_webhook` в отдельном потоке через `asyncio.to_thread`, чтобы HTTP-запросы Moyklass не блокировали event loop.
3. Для поддерживаемого события обработчик возвращает `{"phone": ..., "text": ...}`. Если у пользователя включён `unsubscribe_automailing`, событие не поддерживается или данных нет, обработчик возвращает `None`.
4. Пара телефона и сообщения попадает в `message_queue`.
5. `message_sender_worker` пытается отправить сообщение и через MAX, и через Telegram. Достаточно успеха хотя бы одного канала; если оба канала неуспешны, сообщение повторяется максимум три раза. Между обработками worker ждёт `SEND_INTERVAL`.

Поддерживаемые события: `payment_new` и `sub_lesson_in_debt`. Вебхук ожидает поля внутри `object`; их точный набор виден в обращениях `webhook_handler.py` к Moyklass API.

## Настройки и локальные данные

Не читай и не выводи значения `.env`, сессий мессенджеров, кешей получателей, логов с персональными данными или QR-кода. `.env` уже исключён из Git. Для конфигурации используются имена переменных:

- Moyklass: `MOYKLASS_BASE_URL`, `MOYKLASS_API_KEY`; интеграционный тест использует `MOYKLASS_API_KEY_TEST`.
- Telegram: `TG_API_ID`, `TG_API_HASH`, `TG_PHONE_NUMBER`.
- Сервер: `PORT` (по умолчанию `8000`).
- MAX: `ENABLE_MAX` (по умолчанию включён; `run_project_without_max.py` задаёт `false` автоматически).

Локальные/секретные данные включают `admin_session.session`, `tg_entity_cache.json`, `max_cache/`, MAX-сессию и `max_qr.png`. Не добавляй их в коммиты и не меняй их для проверки.

## Правила безопасной работы

- Не запускай `final_test.py`: он создаёт платёж через реальный API Moyklass. Не запускай ручные блоки отправки из `tg_sender.py` и `max_sender.py`: они могут отправить реальные сообщения.
- Не инициируй реальные вебхуки, импорт контактов, отправку сообщений, создание платежей или другие изменяющие действия во внешних сервисах без явного запроса пользователя.
- Не показывай секреты, токены, номера телефонов, содержимое `.env`, файлы сессий и кеши в выводе, документации или коммитах.
- Сохраняй текущую схему очередей, форматы результата обработчика и поведение доставки, если задача прямо не просит их изменить. При изменении доставки отдельно учитывай случай частичного успеха: сейчас успех одного мессенджера завершает попытки для обоих.
- Не меняй версии или набор зависимостей без необходимости задачи; закреплённых версий в `requirements.txt` сейчас нет.
- Предпочитай небольшие целевые изменения. Перед правкой проследи поток данных от endpoint до интеграции и проверь все затронутые вызывающие места.

## Технические особенности и ограничения

- `moyklass_client.py` использует синхронный `requests`; обработка вебхука поэтому вынесена из event loop через `asyncio.to_thread`. Не вызывай этот синхронный API напрямую из async worker без такого переноса или иного неблокирующего решения.
- `tg_sender.py` и `max_sender.py` создают клиентские объекты при импорте. Переменные окружения должны быть доступны до импорта; модули читают `.env` через `python-dotenv`.
- Состояние очередей хранится только в памяти процесса. Очереди и уже принятые, но не обработанные вебхуки теряются при перезапуске.
- Telegram sender возвращает `True` при успехе и `False` при неудаче; MAX sender возвращает `bool`.
- Повторные попытки сейчас выполняются сразу после завершения обеих отправок (с интервалом worker), без отдельного backoff и устойчивого хранилища.
- В `app.py` проверяется внутреннее поле MAX-клиента `max_client._app.started`; изменение версии библиотеки может затронуть эту проверку.
- При включённом MAX запуск приложения прекращается, если MAX не подключился за три попытки. После успешного старта монитор делает не более трёх попыток переподключения; при неудаче приложение продолжает работу через Telegram. В режиме `ENABLE_MAX=false` MAX-клиент и монитор не запускаются.
- В `webhook_handler.py` для проверки отписки сначала загружается пользователь, а обработчики затем могут загрузить его повторно. Учитывай дополнительные запросы к API при изменениях.
- `final_test.py` использует отдельный тестовый ключ, но фиксированный `USER_ID` и реальный endpoint; воспринимай его как сценарий с побочным эффектом, а не как unit-тест.
- В репозитории нет README и настроенного тестового фреймворка. Не предполагай, что тесты можно безопасно запускать без проверки их содержимого.

## Рабочий процесс агента

1. Перед изменениями изучи относящиеся к задаче файлы и `git status`; не перезаписывай пользовательские изменения.
2. Для новой логики отделяй чистое преобразование данных от сетевых вызовов, если это укладывается в задачу. Для проверки используй фикстуры/моки, а не реальные аккаунты и API.
3. Выполняй только безопасные проверки, относящиеся к изменению. Не запускай интеграционные сценарии, тестовый платеж или отправку сообщения без явной авторизации.
4. Если проверка невозможна без секретов или доступа к внешнему сервису, сообщи это явно и укажи, что именно осталось непроверенным.
5. В итоговом сообщении кратко перечисли изменения, проверки и ограничения/риски.

## Команды

Запуск FastAPI из корня проекта после установки зависимостей и настройки `.env`:

```powershell
python -m uvicorn app:app --host 127.0.0.1 --port 8000
```

Проверка доступности сервера:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
```

Linux-скрипт `run_project.py` сам создаёт `venv`, устанавливает зависимости и запускает сервис с MAX в Screen. `run_project_without_max.py` запускает его без MAX. В Windows эти скрипты не запускают сервер. Команды отправки/создания платежей не являются безопасными проверками.
